Grove migrations are Go code, not SQL files. Any Go module can register migrations into named groups with dependency-aware ordering. Forge extensions ship their own migrations that compose automatically.

## Key Concepts

- Migrations are Go functions, not SQL files, so they can hold logic, conditionals and data transformations.
- Groups: migrations belong to named groups (for example `"core"` or `"forge.billing"`).
- Dependencies: a group declares the groups it depends on with `migrate.DependsOn`.
- Ordering: the orchestrator sorts groups by dependency, then migrations by version.
- Transactions: on PostgreSQL, a migration registered with `Add` or `Define` and the row that records it run in one transaction, unless you opt out with `migrate.NoTransaction()`. Struct migrations run without one unless they set `Transactional: true`.
- Locking: a lock stops two processes from migrating at once (an advisory lock on PostgreSQL and MySQL, a row in `grove_migration_locks` on SQLite and the others).

## Defining Migrations

The quickest way to write a migration is `Group.Add`, in a file whose name carries the version. Declare the group once (`var Migrations = migrate.NewGroup("core")`), then put each migration in its own file. This one is `20240101000000_create_users.go`:

```go
package core

import (
    "context"

    "github.com/xraph/grove/migrate"
)

func init() {
    Migrations.Add(
        func(ctx context.Context, db *migrate.DB) error {
            return db.NewCreateTable("users").
                IfNotExists().
                Column("id", migrate.BigSerial, migrate.PrimaryKey()).
                Column("name", migrate.Text, migrate.NotNull()).
                Column("email", migrate.Text, migrate.NotNull(), migrate.Unique()).
                Exec(ctx)
        },
        func(ctx context.Context, db *migrate.DB) error {
            return db.NewDropTable("users").IfExists().Exec(ctx)
        },
    )
}
```

The `*migrate.DB` your functions receive has schema builders, plus `Exec` and `Query` for raw SQL. The builders work on PostgreSQL and MongoDB, with each driver doing what its database can, and on PostgreSQL the migration runs in a transaction. [Migration Builders](/docs/migrations/builders) covers all of it.

`Add` takes the version and the name from the file name, `<14 digit version>_<name>.go`, and panics at startup when the name doesn't fit.

<Callout type="warn">
A file whose name ends in `_test`, or in a GOOS or GOARCH name such as `_linux`, `_arm64` or `_js`, is left out of the build by the Go toolchain. A migration in one of those files never registers, and nothing tells you.
</Callout>

If you'd rather spell out the version yourself, or you need the raw executor, register a struct. It receives a `migrate.Executor` and doesn't run in a transaction unless you set `Transactional: true`. You can write its statements by hand, as below, or wrap the executor with `migrate.NewDB(exec)` to use the builders (see [Struct Migrations](/docs/migrations/builders#struct-migrations)):

```go
func init() {
    Migrations.MustRegister(&migrate.Migration{
        Name:    "create_users",
        Version: "20240101000000",
        Up: func(ctx context.Context, exec migrate.Executor) error {
            _, err := exec.Exec(ctx, `CREATE TABLE IF NOT EXISTS users (
                id    BIGSERIAL PRIMARY KEY,
                name  TEXT NOT NULL,
                email TEXT NOT NULL UNIQUE
            )`)
            return err
        },
        Down: func(ctx context.Context, exec migrate.Executor) error {
            _, err := exec.Exec(ctx, `DROP TABLE IF EXISTS users`)
            return err
        },
    })
}
```

`migrate.Define(version, name, up, down, opts...)` sits in between. It takes the same `*migrate.DB` functions as `Add`, with the version and name passed in.

## Running Migrations

The orchestrator runs your migrations through a `migrate.Executor`, which has `Exec` and `Query` for raw SQL (plus the tracking and lock methods it uses itself). Migrations written with `Add` or `Define` get that executor wrapped in a `*migrate.DB`, which puts the schema builders on top. Struct migrations get the executor as it is. They can write SQL by hand (or BSON commands for MongoDB), or wrap it with `migrate.NewDB(exec)` to reach the builders.

```go
import "github.com/xraph/grove/drivers/pgdriver/pgmigrate"

// Create a driver-specific executor
executor := pgmigrate.New(pgdriver.Unwrap(db))

// Create the orchestrator with the executor
orchestrator := migrate.NewOrchestrator(executor,
    core.Migrations,
    billing.Migrations,
)

// Migrate up
result, err := orchestrator.Migrate(ctx)
fmt.Printf("Applied %d migrations\n", len(result.Applied))

// Rollback last migration
result, err = orchestrator.Rollback(ctx)

// Check status
statuses, err := orchestrator.Status(ctx)
```

## Migration Table

Grove tracks migration state in `grove_migrations` (the PostgreSQL form, from `migrate.MigrationTableSchema()`):

```sql
CREATE TABLE IF NOT EXISTS grove_migrations (
    id          BIGSERIAL PRIMARY KEY,
    version     VARCHAR(14) NOT NULL,
    name        VARCHAR(255) NOT NULL,
    "group"     VARCHAR(255) NOT NULL,
    migrated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE(version, "group")
);
```

Each driver's executor creates the tracking table (and, where it uses one, the `grove_migration_locks` table) in its own dialect.

## Executor Registry

The executor registry provides driver-agnostic executor creation through auto-registration. Each driver's migrate package registers its factory via `init()`, so a blank import is all you need.

### Auto-Registration

Import the driver's migrate package to register its executor factory:

| Import | Registered Name |
|--------|----------------|
| `_ "github.com/xraph/grove/drivers/pgdriver/pgmigrate"` | `pg` |
| `_ "github.com/xraph/grove/drivers/mysqldriver/mysqlmigrate"` | `mysql` |
| `_ "github.com/xraph/grove/drivers/sqlitedriver/sqlitemigrate"` | `sqlite` |
| `_ "github.com/xraph/grove/drivers/tursodriver/tursomigrate"` | `turso` |
| `_ "github.com/xraph/grove/drivers/clickhousedriver/clickhousemigrate"` | `clickhouse` |
| `_ "github.com/xraph/grove/drivers/mongodriver/mongomigrate"` | `mongo` |

### Using the Registry

Once registered, create executors from any driver dynamically:

```go
import "github.com/xraph/grove/migrate"

executor, err := migrate.NewExecutorFor(db.Driver())
if err != nil {
    // No factory registered for this driver
    log.Fatal(err)
}

orch := migrate.NewOrchestrator(executor, core.Migrations)
```

### Manual Registration

Register a custom executor factory for drivers not included in Grove:

```go
migrate.RegisterExecutor("custom", func(drv any) migrate.Executor {
    return myCustomExecutor(drv)
})
```

### Listing Registered Executors

```go
names := migrate.Executors()
fmt.Println("Registered executors:", names) // e.g. [pg mysql sqlite]
```

<Callout type="info">
With the Grove Forge extension you still need the blank import for your driver's migrate package. The extension then finds the executor through the registry.
</Callout>
