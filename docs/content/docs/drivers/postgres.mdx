The PostgreSQL driver is Grove's primary driver, built on [pgx](https://github.com/jackc/pgx) for high-performance connection pooling and native protocol support.

## Installation

```bash
go get github.com/xraph/grove
go get github.com/jackc/pgx/v5
```

## Connection

```go
import (
    "github.com/xraph/grove"
    "github.com/xraph/grove/driver"
    "github.com/xraph/grove/drivers/pgdriver"
)

// 1. Create and open the driver
pgdb := pgdriver.New()
pgdb.Open(ctx, "postgres://user:pass@localhost:5432/mydb?sslmode=disable", driver.WithPoolSize(20))

// 2. Pass the connected driver to Grove
db, err := grove.Open(pgdb)
if err != nil {
    log.Fatal(err)
}
defer db.Close()
```

## Native Syntax

The PostgreSQL driver supports the full range of PostgreSQL-specific syntax:

### Placeholders

PostgreSQL uses `$1`, `$2`, etc. for parameterized queries:

```go
db.NewSelect(&users).
    Where("email ILIKE $1", "%@example.com").
    Where("created_at > $2", time.Now().AddDate(0, -1, 0)).
    Scan(ctx)
```

### DISTINCT ON

```go
db.NewSelect(&users).
    DistinctOn("department").
    OrderExpr("department, created_at DESC").
    Scan(ctx)
```

### JSONB Operators

```go
db.NewSelect(&users).
    Where("metadata->>'role' = $1", "admin").
    Where("metadata @> $1::jsonb", `{"active": true}`).
    Scan(ctx)
```

### FOR UPDATE / FOR SHARE

```go
db.NewSelect(&account).
    Where("id = $1", accountID).
    ForUpdate().
    Scan(ctx)
```

### ON CONFLICT (Upsert)

```go
db.NewInsert(&user).
    OnConflict("(email) DO UPDATE").
    Set("name = EXCLUDED.name").
    Set("updated_at = NOW()").
    Returning("*").
    Exec(ctx)
```

### RETURNING

```go
var insertedUser User
db.NewInsert(&user).
    Returning("*").
    Scan(ctx, &insertedUser)
```

### LISTEN / NOTIFY

```go
pgdb := pgdriver.Unwrap(db)

// Create a listener and register a callback
listener := pgdb.NewListener()
listener.OnNotification("events", func(n *pgdriver.Notification) {
    fmt.Printf("channel=%s payload=%s\n", n.Channel, n.Payload)
})

// Start listening and subscribe to the channel
listener.Start(ctx)
listener.Listen(ctx, "events")

// ... later, when done:
listener.Close()
```

## Connection Pool Options

```go
pgdb := pgdriver.New()
pgdb.Open(ctx, dsn,
    driver.WithPoolSize(20),
    driver.WithQueryTimeout(30 * time.Second),
)
db, err := grove.Open(pgdb)
```

## Migrations

The `pgmigrate` package is the PostgreSQL migration executor. Build one from the driver and hand it to an orchestrator:

```go
import (
    "github.com/xraph/grove/drivers/pgdriver"
    "github.com/xraph/grove/drivers/pgdriver/pgmigrate"
    "github.com/xraph/grove/migrate"
)

executor := pgmigrate.New(pgdriver.Unwrap(db))
orchestrator := migrate.NewOrchestrator(executor, Migrations)

result, err := orchestrator.Migrate(ctx)
```

Migrations written with `Group.Add` get the schema builders from [Migration Builders](/docs/migrations/builders), and `db.Exec` is there for anything they don't cover. This section is about what PostgreSQL does with them.

### Transactions

Each `Add` or `Define` migration and the row that records it run in one transaction, on the connection that holds the migration lock. The lock is a session advisory lock, which is why the executor keeps one dedicated connection for the whole run. A failure or a panic rolls everything back and leaves no applied record.

Opt out with `migrate.NoTransaction()`. You need it for `CREATE INDEX CONCURRENTLY` and `DROP INDEX CONCURRENTLY`, because PostgreSQL refuses both inside a transaction, and `DROP INDEX CONCURRENTLY` can't be combined with `Cascade()`. The [Transactions](/docs/migrations/builders#transactions) section of Migration Builders has a full example.

Calling a migration's `Up` or `Down` yourself, as a test would, runs it with no transaction. An operation that renders as several statements, such as an `ALTER TABLE` split around a rename, isn't atomic then. If the driver can't give the migration a dedicated connection, the orchestrator runs it without a transaction rather than failing.

### Types

The type table in [Migration Builders](/docs/migrations/builders#types) lists the PostgreSQL name of each builder type. A few are worth knowing by heart: `migrate.Timestamp` is `TIMESTAMPTZ`, `migrate.JSON` is `JSONB`, `migrate.Float` is `DOUBLE PRECISION` and `migrate.Bytes` is `BYTEA`. `migrate.Numeric(10, 2)` becomes `NUMERIC(10, 2)`, and `migrate.ArrayOf(migrate.Text)` becomes `TEXT[]`.

Anything else goes through `migrate.Type`, which passes its string to PostgreSQL untouched:

```go
Column("name", migrate.Type(`TEXT COLLATE "C"`))
Column("addr", migrate.Type("INET"))
```

### Defaults and Quoting

`migrate.Default(value)` renders a literal. Strings are single-quoted with embedded quotes doubled, which assumes `standard_conforming_strings` is on (it is by default). Booleans become `TRUE` or `FALSE`, integers print as they are, and floats print in their shortest form, so `Default(1.0)` renders as `1`. Use `migrate.DefaultExpr` when you need an exact decimal, or anything else that isn't a plain string, boolean, integer or float:

```go
Column("rate", migrate.Numeric(6, 4), migrate.NotNull(), migrate.DefaultExpr("0.0250"))
```

Every identifier is quoted, so reserved words work as table and column names. A column called `group` or a table called `order` needs nothing special.

### Joined ALTER TABLE

Neighbouring actions in one `NewAlterTable` become a single `ALTER TABLE`, and a rename gets a statement of its own. Inside the joined statement PostgreSQL runs the subcommands in its own pass order, not strictly the order you wrote. Contradictory actions on one column, such as `SetNotNull` and then `DropNotNull`, don't behave as written, so put them in separate `NewAlterTable` calls.

## Compatible Databases

### CockroachDB

[CockroachDB](https://www.cockroachlabs.com/) is PostgreSQL wire-compatible. The pgdriver works with CockroachDB out of the box with a few caveats:

```go
pgdb := pgdriver.New()
err := pgdb.Open(ctx, "postgresql://root@localhost:26257/mydb?sslmode=disable",
    driver.WithPoolSize(20),
)
```

**Known differences:**

- `LISTEN/NOTIFY` is not supported -- CockroachDB does not implement PostgreSQL's pub/sub system
- `DISTINCT ON` works but may behave differently with distributed query execution
- `SERIAL` columns should be replaced with `UUID` or `INT DEFAULT unique_rowid()` for distributed ID generation
- Advisory locks (`pg_advisory_lock`) are not supported -- use CockroachDB's built-in locking

### Neon

[Neon](https://neon.tech/) is serverless PostgreSQL. The pgdriver works directly with Neon:

```go
pgdb := pgdriver.New()
err := pgdb.Open(ctx, "postgresql://user:pass@ep-example-123.us-east-2.aws.neon.tech/mydb?sslmode=require",
    driver.WithPoolSize(5), // Keep pool size small for serverless
)
```

**Tips for Neon:**

- Use `sslmode=require` in the DSN
- Keep connection pool size small (5-10) since Neon uses a connection pooler (pgbouncer)
- Cold starts may add latency on the first connection -- consider using Neon's connection pooler endpoint
- All PostgreSQL features (JSONB, LISTEN/NOTIFY, CTEs, etc.) are fully supported

### Supabase

[Supabase](https://supabase.com/) provides hosted PostgreSQL. The pgdriver connects directly:

```go
pgdb := pgdriver.New()
err := pgdb.Open(ctx, "postgresql://postgres.[project-ref]:[password]@aws-0-us-east-1.pooler.supabase.com:6543/postgres",
    driver.WithPoolSize(10),
)
```

**Tips for Supabase:**

- Use the pooler connection string (port 6543) for application connections
- Use the direct connection string (port 5432) for migrations
- All PostgreSQL features are supported, including RLS (Row Level Security)
